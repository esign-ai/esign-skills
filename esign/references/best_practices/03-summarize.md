# 总结场景

> 能力入口见 [总结能力](../products/summarize.md)。本文件是场景 recipe 表 + 深挖小节；通用规范（并行、翻页、ID 传递）见 [_common/conventions.md](_common/conventions.md)。recipe 为推荐组合（不吻合时可自行组合）；具体判断、边界与输出仍以能力主体及其引用规则为准。

| Recipe | 行动指南（推荐路线） |
|--------|-------------------|
| summarize-from-file | 1. 使用本轮明确文件、有效已选目标或用户指向的真实列表对象；多份候选而指向不明只澄清目标，不搜索合同、不要求内部 ID<br>2. 本地文件：`esign document extract-contract-body --file '<文件的真实可访问路径>'`；已选平台文件：`esign document extract-contract-body --file-key '<真实fileKey>'`。两种方式择一<br>3. 核对 `code == "0"` 且 `data.content` 非空；长合同分段读取后再汇总，只提供片段时仅说明影响结论的缺口<br>4. 按 [摘要与字段规则](../products/summarize/summary-rules.md) 从正文识别类型、生成 200—300 字概述、按实际重要性筛选关键字段；每个字段附足以支持该事实的逐字连续原文<br>5. 将本轮实际读取的正文原样保存为 UTF-8 `source.txt`，不先摘要、不改写原文迎合提取结果 |
| summarize-from-text | 1. 本轮明确粘贴的正文直接使用，标记为「本次提供的合同正文」，不运行抽取<br>2. 未提供内容不视为已读；缺文件只引导上传并等待，不提前问主体、金额、类型或字段偏好<br>3. 取得正文后从 summarize-from-file 第 4 步起同 |
| summarize-multi | 1. 用户明确要求多份或「全部摘要」时，按指定顺序或可靠选择顺序建立队列，逐份处理<br>2. 一份文件输出一份摘要，不混合事实；不将候选列表自动视为全选，不每份都要求回复「继续」<br>3. 独立文件失败不阻塞其他已明确文件；保留已完成、失败及待处理项，暂停仅因目标歧义、读取失败或执行限制 |
| summarize-validate | 1. 按 [结果协议与校验](../products/summarize/result-schema.md) 组织 `summary_payload.json`（`schema_version: "2.0"`；`coverage`／`overviewText`／`contractTypeText`／`tableRows` 全必填；每行 `quotes` 为逐字连续原文数组）<br>2. `python3 '<本技能目录>/scripts/validate_summary.py' --input-file '<本轮summary_payload.json>' --text-file '<本轮source.txt>' --output-json '<本轮summary_result.json>'`（入参见下方「校验入参」）<br>3. 退出码为 0、stdout 是合法结果且指定 JSON 存在才算完成；失败时按真实原文修正，最多修正重跑两次，不得静默丢字段或改来源求通过<br>4. 校验通过仍须复核字段归属、条件完整、简洁事实与原文是否一致；不生成摘要报告、预览文件或下载链接 |
| summarize-followup | 1. 退出成功并取得有效结果后，直接在对话先给 200—300 字事实概述，再将主体、总金额、标的及必要期限拆为简短字段；不展示覆盖范围、JSON、校验协议或运行日志<br>2. 用户询问依据时直接在对话引用相关原文并说明对应事项，不给孤立证据编号，不另开报告<br>3. 「继续下一份」只使用真实未完成队列；明确指定新范围时以新范围为准，重试指定失败项、不重复已完成文件<br>4. 用户取消即停止；文件或企业改变时按来源规则重新核对，不沿用不匹配结果 |

## 概述口径（200—300 字）

- 基于当前文件说明**交易目的、主要内容、核心履行安排**；只写合同事实，不引入风险评价、行业惯例或签署建议。
- 不把下方结构化字段逐项复述一遍；材料过少不能支撑 200 字时，以真实事实为先，不用重复或无关信息凑数。
- 固定结构（概述＋核心信息），**不存在简明／详细模式**，不询问用户选择详略或字段偏好；用户明确限定「只看金额」「总结 3 条」时直接遵从。

## 结构化字段表

- 按合同实际重要性筛选，不凑 12—15 行、不搬出全部条款。每个字段包含一个明确事实，已在概述完整表达的项不在其他标题重复。
- 主体各列一项，只有原文明确对应才写「甲方（买方）」，不凭惯例指定买卖角色、不推定「我方」；合同可多方，不强套双方模板。
- 总金额单列并保留币种与原文含税口径；押金、保证金、标的小计**不混入**总价。标的名称／数量／单价／小计分开，多个标的可用简短明细表。
- 付款节点、交付期限确有必要时另列，保留触发条件；分期按节点区分。合同编号仅在辨识需要时列，联系方式、份数、重复定义、一般条款默认省略。

## 多份逐份 vs 合并的边界

- 用户明确要求多份或「全部摘要」才逐份处理；一份文件输出一份摘要，**不混合事实**，不把候选列表自动视为全选。
- 独立文件失败不阻塞其他已明确文件；只暂停于目标歧义、读取失败或执行限制，保留已完成／失败／待处理项。
- 不每份都要求回复「继续」；用户明确后连续处理已完成队列，用户取消即停。

## 校验入参

```bash
python3 '<本技能目录>/scripts/validate_summary.py' --input-file '<本轮summary_payload.json>' --text-file '<本轮source.txt>' --output-json '<本轮summary_result.json>'
```

- `schema_version: "2.0"`；`coverage`／`overviewText`／`contractTypeText`／`tableRows` 全必填，不增加字段，示意值必须换成本次事实。
- 每行 `quotes` 为逐字连续原文（含换行与标点），多处依据分段保存，不拼造连续引文、不为命中改写来源。
- `coverage.status` 为 `complete` 或 `partial`；缺页、截断、未读正文用 `partial` 并说明具体 `limitations`，不能由命令成功推定完整。
- 只处理当前选定文件、不联网、不建卡片、不保存远端记录；输出不能覆盖输入；JSON 与校验日志默认不展示给用户。

## 关键区分

- **总结 vs 审查**：总结只提炼事实与核心信息，不作风险审查、签署建议或等级判断；审查逐条评风险并出报告。
- **总结 vs 问答**：总结面向整份合同输出概述＋关键字段；问答针对某个具体条款或事项作答，不产出整份摘要。
- **总结 vs 比对**：总结处理单份文件；比对识别两份文件之间的版本差异，不生成摘要。
- **概述 vs 字段**：概述 200—300 字讲交易目的与核心履行安排，不逐项重复字段；字段按实际重要性拆开，不搬全部条款凑行。
- **事实 vs 评价**：只写合同写明的事实，不加行业惯例、风险可控等评价；推算值不得冒充原文载明金额，文本约定日期不得写成已实际签署。
