# 提问与答案处理规则

仅用于当前能力 `index.md` 列出的提问节点。首稿前按依赖组织必要问题，使用宿主实际可用的提问能力；不绑定具体工具名或猜测参数。原有初稿后自然语言补充、文件确认和签署衔接保持各自规则。

## 组织当前可问的问题

1. 先读取用户输入、已读底稿和当前有效事实，列出真正缺失的起草立场及结构必要信息。已知不问，不把名称、金额、日期等可后补事实加入首稿前问题。
2. 扫描所有必要缺口，而不是只取问题队列的第一项。只有出现条件、问法和选项均可确定，且不依赖本批其他未知答案的问题，才放进同一批。
3. 若 B 依赖 A，而 C 与 A 独立，先问 A、C，收到提交后再决定 B。不因遇到 B 就把仍可同批询问的 C 推迟，也不提前猜 B 的选项。
4. 同一决定只问一次；不把多个独立决定塞进一个复合问题。题数由真实缺口决定，可以只有一项，不凑数、不增加下一阶段的问题。按实际工具限制调用，不能为减少轮次而给出含糊或不适用的问题。
5. 基于底稿时先取得并读取文件；缺文件只引导上传，不能提前猜角色或搜索用户电脑。选择底稿与依赖底稿内容的问题不能放在同一批。

## 使用提问工具

- 以本次实际暴露的工具定义为准，区分一道题的多选与一次调用承载多道题。工具支持本批问题数量及所需回答方式时，一次传入本批问题；只有一道题时可以使用单题能力。
- 工具不支持整批问题、缺少所需回答方式或不可用时，用一条简短文字消息列出同批必要问题，统一接收回复。不要连续调用多个单题工具模拟批量，不试猜字段或工具名，不向用户解释内部适配过程。
- 开放的业务描述可使用工具实际支持的自由输入；不支持时按上述规则用文字收集，不生成虚构选项。文件上传及初稿后的普通事实补充仍沿用原流程。
- 发出问题后等待用户实际提交。预选、空返回、超时或界面关闭不作为答案；未提交内容不作为已确认事实。用户通过普通文字提供明确答案时直接处理，不要求必须点击。

## 问题与选项

- 问法简短、业务化，选项之间容易区分。有说明字段时仅补充判断所需的信息，不展示内部 ID、命令或日志。
- 文件和主体等对象选项来自用户或真实数据，保留选项与对象的对应关系。合同类型等概念选项可以使用常见分类，但不能把分类当作已知事实。
- 角色选项以当前已知交易为依据；合同类型未知时不提前固定买方／卖方等选项。适用时提供平衡立场，不能将未作答视为选择平衡。
- 若宿主已经提供其他补充或自由输入，不重复添加同义入口。自由输入中的选择、背景、纠正和新增事实须整体理解。
- 候选过多时按实际条件缩小范围，不静默遗漏候选。无法唯一识别对象或字段时只澄清该项，不按常识猜测。

## 收到答案后

- 一次吸收整批实际提交的明确答案，以及自由输入和普通文字回复中携带的额外事实。保留问题与答案的对应关系；一条回复已回答多个缺口时全部复用，不重复询问。
- 只将含义明确、可以对应当前问题的内容记为已知；未回答项仍是缺口。对“还没问过立场”“没有回答立场”和“明确选择平衡”分别处理，不因为已完成类型询问就默认中性起草。
- 以用户最新有效提交中明确表达的修改为准。采购改为租赁等前提变化时，保留仍适用的事实，重新判断原有角色、立场和结构答案；不机械沿用不相容答案，也不要求重答全部问题。
- 同一次提交包含矛盾且无法判断真实意图时，仅澄清冲突点，不把冲突内容回显为已确认。对迟到或重复回答先检查其与当前任务的关系，不让旧答案覆盖新事实或再次生成同一结果。
- 结构足够且立场明确就直接生成完整初稿；只有仍阻断起草的缺口或冲突才继续按依赖合批询问，不增加信息收集完成后的确认关卡。
- 用户取消任务就停止。提问调用结果不明时先核对是否已展示或已收到回复，避免重复发送；实际未收到答案时保持等待，不擅自继续。

## 输出与业务边界

需要时可用一句业务语言承接已明确的类型和立场，随后直接出稿，不要求用户再次确认，不复述整套问答记录、不输出内部校验结论。存在未解决冲突时只询问冲突。

回答起草问题不代表授权发送合同、审批或签署。正式文件交付及签署确认继续遵循[文件交付与签署衔接](delivery-rules.md)，不因问答合批而跳过。
